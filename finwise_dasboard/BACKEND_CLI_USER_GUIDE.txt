======================================
Practical instructions for the assignment demonstration
Version: 1.0 | Python 3.10+ | No external packages required

This guide describes the ACTUAL features of complete_budgeting_framework.zip.
All examples use synthetic HKD data. No recommendation system is included.

1. FIRST-TIME SETUP
-------------------
A. Extract complete_budgeting_framework.zip.
B. Open a terminal (Command Prompt, PowerShell, macOS Terminal, etc.).
C. Change directory to the extracted budgeting_framework folder.
D. Check Python:

   python --version

   On some systems use 'python3' instead of 'python' in ALL commands.

E. Load the sample transactions:

   python cli.py --db demo.sqlite3 import sample_transactions.json

F. Set a monthly budget of HK$3,000:

   python cli.py --db demo.sqlite3 set-budget 3000

G. Load the sample configuration:

   python cli.py --db demo.sqlite3 set-config sample_config.json

H. Add the example confirmed bill:

   python cli.py --db demo.sqlite3 add-bill sample_confirmed_bill.json

I. Generate the report (use the example's October date):

   python cli.py --db demo.sqlite3 analyze --date 2026-10-15

The commands print output in the terminal. The analysis output is JSON.

IMPORTANT: Always use the same '--db demo.sqlite3' argument. If you omit
it, the CLI opens a DIFFERENT database named budget.sqlite3.

2. HOW THE DATABASE WORKS
-------------------------
The file demo.sqlite3 is a local SQLite database created automatically.
It stores transactions, settings, and confirmed bills across runs.
You do NOT need to re-import the sample transactions every time.

There are three ways to interact with the prototype:
  - CLI commands in cli.py for common operations.
  - JSON files for transaction imports, configuration, and bills.
  - Short Python commands for database operations not exposed by the CLI.

3. ADD A NEW TRANSACTION
------------------------
The CLI imports a JSON ARRAY of one or more transactions.

A. Create a file named new_transaction.json with the following contents:

[
  {
    "id": "lunch-001",
    "date": "2026-10-12",
    "amount": "65.00",
    "kind": "expense",
    "category": "Food",
    "merchant": "Campus Canteen",
    "account": "Hang Seng",
    "status": "posted",
    "currency": "HKD"
  }
]

B. Run:

   python cli.py --db demo.sqlite3 import new_transaction.json

C. Run the analysis again:

   python cli.py --db demo.sqlite3 analyze --date 2026-10-15

The new transaction is saved, and the current-month spending is recalculated.

Transaction fields:
  id       Unique identifier. Required. Use a different ID for each purchase.
  date     Transaction date in YYYY-MM-DD format. Required.
  amount   Nonnegative amount, preferably as a quoted string. Required.
  kind     expense, income, refund, or transfer. Required.
  category Spending category, e.g. Food, Transport, Shopping.
  merchant Store or payee name, e.g. Campus Canteen.
  account  Account label, e.g. Hang Seng.
  status   posted (default), pending, or cancelled.
  currency Three-letter currency code; HKD is the default.

Notes:
  - 'income' records money received; it does not increase the monthly
    spending budget automatically.
  - 'refund' reduces net spending.
  - 'transfer' is excluded from spending totals.
  - Only 'posted' transactions count toward the spending summary.
  - The analysis supports one currency at a time; the default is HKD.
  - To add several transactions at once, place several objects in the same
    JSON array, separated by commas.

4. UPDATE AN EXISTING TRANSACTION
--------------------------------
The import command also UPDATES an existing transaction when its ID matches.

For example, suppose lunch-001 was actually HK$75, not HK$65.
Edit new_transaction.json, changing:

   "amount": "65.00"

to:

   "amount": "75.00"

Then import it again:

   python cli.py --db demo.sqlite3 import new_transaction.json

The original lunch-001 record is replaced with the updated values.
IMPORTANT: Keep the SAME ID. A new ID creates another transaction instead.

You can also change the date, category, merchant, account, kind, or status
by changing the JSON object and re-importing it with the same ID.

5. DELETE A TRANSACTION
-----------------------
There is no 'delete' subcommand in the current CLI. However, deletion is
already implemented in storage.py as BudgetStore.delete_transaction().

To delete the transaction with ID lunch-001, run this one-line command
from the budgeting_framework folder:

   python -c "from storage import BudgetStore; db=BudgetStore('demo.sqlite3'); db.delete_transaction('lunch-001'); db.close()"

Then run the analysis again:

   python cli.py --db demo.sqlite3 analyze --date 2026-10-15

The deleted transaction no longer contributes to spending calculations.
WARNING: Deletion is permanent within the local database; back up the
.sqlite3 file first if you might need to restore it.

6. VIEW SAVED TRANSACTIONS
--------------------------
There is no 'list' subcommand in the current CLI. You can view the saved
records using this existing storage function:

   python -c "from storage import BudgetStore; db=BudgetStore('demo.sqlite3'); print(*db.transactions(), sep='\n'); db.close()"

This prints each transaction as a Python dictionary.

7. CHANGE THE MONTHLY BUDGET
----------------------------
To set or replace the budget, for example HK$4,000:

   python cli.py --db demo.sqlite3 set-budget 4000

To change it again to HK$2,500:

   python cli.py --db demo.sqlite3 set-budget 2500

Run the report again after any change:

   python cli.py --db demo.sqlite3 analyze --date 2026-10-15

The budget is a single setting used for the selected analysis month.
The prototype does not yet store different budgets for different months.

8. UPDATE ESSENTIAL RESERVES, CASH, BUFFERS, AND CATEGORY LIMITS
-----------------------------------------------------------------
Open sample_config.json in a text editor. It initially resembles:

{
  "currency": "HKD",
  "lookback_months": 3,
  "essential_reserves": {"Utilities": "150"},
  "expected_other_spending": "300",
  "safety_buffer": "200",
  "spendable_cash": "1800",
  "unpaid_cash_obligations": "150",
  "cash_buffer": "200",
  "category_caps": {"Groceries": "700", "Transport": "300"}
}

What these settings mean:
  currency                 Analysis currency. Transactions must match it.
  lookback_months          How many completed past months to examine (1–24).
  essential_reserves       Unpaid essential expenses to protect in the budget.
  expected_other_spending  Estimated future spending not already in reserves.
  safety_buffer            Additional budget amount protected against surprises.
  spendable_cash           Money currently available to spend; entered manually.
  unpaid_cash_obligations  OTHER cash obligations, excluding confirmed bills.
  cash_buffer              Additional cash protection.
  category_caps            User-defined maximum MONTHLY amounts per category.

Example: You now expect HK$300 in unpaid utility bills instead of HK$150.
Change:

   "essential_reserves": {"Utilities": "300"}

Then save the file and run:

   python cli.py --db demo.sqlite3 set-config sample_config.json
   python cli.py --db demo.sqlite3 analyze --date 2026-10-15

IMPORTANT: 'set-config' REPLACES the entire saved configuration object.
Keep all the settings you want in the JSON file when you save it.

For a useful demonstration, try increasing 'safety_buffer' from 200 to 500.
The safe discretionary spending limit should decrease, all else equal.

Do not count the same future expense twice within 'essential_reserves'.
The cash and budget constraints are separate, so the same bill may need to
be represented once in each constraint if it affects both.

9. ADD OR UPDATE A CONFIRMED BILL
--------------------------------
Create a file called new_bill.json containing ONE bill object (not an array):

{
  "id": "phone-oct",
  "name": "Mobile phone plan",
  "category": "Utilities",
  "due": "2026-10-25",
  "amount": "120.00",
  "currency": "HKD"
}

Run:

   python cli.py --db demo.sqlite3 add-bill new_bill.json

This stores the confirmed bill for the forecast AND safe-spending calculation.
To UPDATE that bill, change its amount or due date in new_bill.json and
run the same command again using the SAME bill ID.

IMPORTANT DISTINCTION:
  - Adding a confirmed future bill updates both the FORECAST and SAFE spending.
  - You do NOT need to add that bill separately to essential_reserves.
  - For a reserve in the SAME category, the engine protects the larger amount.
  - The unpaid_cash_obligations input excludes confirmed bills to avoid
    double-counting in cash calculations.
  - Remove/update a confirmed bill if paid before its scheduled due date.
  - Confirmed bills are one-time entries; next month is not auto-scheduled.

10. VIEW OR DELETE A CONFIRMED BILL
----------------------------------
View all confirmed HKD bills:

   python -c "from storage import BudgetStore; db=BudgetStore('demo.sqlite3'); print(*db.confirmed_bills('HKD'), sep='\n'); db.close()"

There is no dedicated bill-delete CLI command or public delete-bill method.
If you need to delete a bill, use the SQLite connection exposed by BudgetStore:

   python -c "from storage import BudgetStore; db=BudgetStore('demo.sqlite3'); db.conn.execute('DELETE FROM confirmed_bills WHERE id=?', ('phone-oct',)); db.conn.commit(); db.close()"

This removes the bill with ID phone-oct. It does NOT remove any related
amount you manually entered in 'essential_reserves'. Update that
configuration separately if necessary.

11. RUN THE FULL BUDGETING ANALYSIS
----------------------------------
Run:

   python cli.py --db demo.sqlite3 analyze --date 2026-10-15

To save the result to a file instead of printing it only on screen:

   python cli.py --db demo.sqlite3 analyze --date 2026-10-15 > report.json

Use a date appropriate for the transactions you entered. For the bundled
sample data, October 15, 2026 is useful. For your own transactions, use
the desired analysis date in YYYY-MM-DD format.

The report includes transaction data-quality checks, spending totals,
historical category baselines, candidate recurring expenses, a month-end
forecast, a dynamic budget plan, unusual transactions for the selected
date, and weekday spending patterns.

12. CHECK WHETHER A PURCHASE IS AFFORDABLE
------------------------------------------
For a proposed HK$350 purchase:

   python cli.py --db demo.sqlite3 purchase 350 --date 2026-10-15

The result contains:
  price                    Proposed purchase price.
  safe_limit               Maximum safe discretionary purchase amount.
  affordable               true or false.
  headroom_after_purchase  Remaining safe allowance (negative if too expensive).
  binding_constraint       Whether cash or budget was the limiting factor.

Try changing the price:

   python cli.py --db demo.sqlite3 purchase 50 --date 2026-10-15
   python cli.py --db demo.sqlite3 purchase 1000 --date 2026-10-15

The checker does not buy anything, update the transaction database, or
reserve the purchase amount. It only evaluates the proposed purchase.

13. HOW TO READ THE REPORT
--------------------------
The main sections in the analysis JSON are:

  quality
    Counts records and flags possible duplicates or uncategorized spending.

  current_month
    Posted income, gross expenses, refunds, net spending, and spending
    breakdowns by category, merchant, and day.

  historical_category_baselines
    Typical spending in each category based on observed prior months.

  recurring_candidates
    Possible weekly, biweekly, monthly, quarterly, or annual payments.
    These are NOT automatically treated as confirmed bills.

  forecast
    Estimated month-end spending, budget variance, and possible overrun.
    Uses historical baselines and current pace. It is an estimate.

  budget_plan
    Monthly budget, amount already spent, protected reserves, budget
    headroom, cash headroom, safe purchase limit, daily allowance, and
    suggested category allocations.

  unusual_transactions_today
    Large transactions on the selected date compared with earlier
    transactions in the same category. Not a fraud determination.

  weekday_spending_patterns
    Descriptive average spending for each weekday.

  warnings
    Known limitations and caveats.

The key result for your assignment demonstration is:

  budget_plan -> safe_discretionary_purchase_limit

This is constrained by BOTH budget headroom and cash headroom when cash
information is provided. It is not a guarantee that spending is safe.

14. RUN TESTS AND RESET THE DEMONSTRATION
-----------------------------------------
Run the automated tests:

   python -m unittest discover -v

The supplied version passed 20 tests when packaged.

To reset the demo WITHOUT losing the original sample JSON files:
  A. Close any programs using demo.sqlite3.
  B. Delete the demo.sqlite3 file using your file manager.
  C. Repeat Section 1, steps E through I.

This recreates the demo database from the sample files.
Do not delete a real database unless you have a backup.

15. SUGGESTED FIVE-MINUTE ASSIGNMENT DEMONSTRATION
--------------------------------------------------
1. Explain that the engine reads transactions and learns spending patterns.
2. Run the sample analysis and point to current_month and recurring_candidates.
3. Add a new transaction using new_transaction.json (Section 3).
4. Run analysis again to show updated spending and budget headroom.
5. Increase the monthly budget using set-budget (Section 7).
6. Change the safety buffer in sample_config.json (Section 8).
7. Add a confirmed bill and explain the forecast-versus-reserve distinction.
8. Run the purchase check for two different prices (Section 12).
9. Optionally delete the new transaction (Section 5) and rerun analysis.

This is sufficient to show a working rule-based budgeting prototype without
building a web interface, a bank integration, or a recommendation system.

16. TROUBLESHOOTING AND IMPORTANT LIMITATIONS
----------------------------------------------
"No such file or directory":
  Make sure you are inside the extracted budgeting_framework directory.

"Set budget first":
  Run: python cli.py --db demo.sqlite3 set-budget 3000

"Mixed currencies":
  The selected analysis currency and all transaction currencies must match.
  No currency conversion is implemented.

"Invalid JSON":
  JSON requires double quotes and commas between objects/fields. Transaction
  import files must contain a JSON array; bill files must contain one object.

"Nothing changed after import":
  Check that you used the same --db filename and that the transaction date
  is on or before the report's selected date.

"Why is a bill not reducing my safe spending limit?":
  Confirm that the bill is due after the report's as-of date and before
  the end of the selected month, and that the app is running version 1.1.
  If a tighter cash constraint already binds, the final safe limit might
  remain unchanged because of that stricter constraint.

"Why is the forecast inaccurate?":
  It is a simple rule-based estimate, not a trained predictive model.
  Incomplete historical data, irregular expenses, and one-off purchases
  can make it inaccurate.

Additional boundaries:
  - No bank synchronization or real-time bank balances.
  - No graphical user interface.
  - No automatic confirmation of detected recurring expenses.
  - No automatic next-month bill creation.
  - No per-month budget history; one saved monthly budget is used.
  - No account-level reconciliation or secure financial-account login.
  - The database is local and is not encrypted by the prototype.
  - The spending forecast and budget reserve calculations are separate.
  - The safe daily allowance covers days AFTER the selected date.
  - Category suggestions are simple historical proportions, not AI optimization.
